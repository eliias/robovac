# robovac — social cards & SEO

Status in this repo: the head metadata lives in `app/layout.tsx` plus per-route `metadata` exports, the origin derives from the request host (no configured base URL), `robots.txt` and `sitemap.xml` are route handlers, and the per-term cards are generated by `scripts/generate-og-cards.mjs` into `public/brand/og/` (committed, regenerate when a term or blurb changes). The term set comes from `lib/terms.ts`, built pages only. The report stays `noindex` with the default card, option (a) below: the no-server-state promise is load-bearing.

Four card templates, the exact `<head>` for every route, and how to generate the per-report and per-term cards at deploy time. Absolute URLs below assume `http://robovac.hannesmoser.at` — replace the origin, keep the paths.

---

## 1. The one thing that is unusual here

**A report URL carries its whole payload in the fragment.** Browsers never send a fragment to the server (RFC 3986 §3.5), and crawlers do not execute your JS before deciding what to show. So:

- A shared report link is, to a scraper, indistinguishable from the bare page. It will preview with whatever `og:image` the shell serves.
- The report itself is **not indexable and should not be**. It contains someone's table names and statistics. Serve it `noindex`, and point `canonical` at the landing page.

You have two options for the report card, in order of cost:

**(a) Accept the default.** Every report link previews as `og-default.png`. Zero infrastructure, and honest: the preview describes the tool, not the table.

**(b) Serve a scraper-visible twin.** When robovac's MCP builds a link, have it also emit a short server-readable form — `/r/<id>?og=1` or a signed query string carrying only the four display fields (table name, heap size, dead tuples, xid age, verdict). The HTML at that URL sets a per-report `og:image` and immediately redirects a real browser to the fragment form. This leaks the table name into a URL your server sees, which is a product decision, not a technical one — the "no server-side state" promise on /mcp is load-bearing, so if you do this, say so there.

Explain pages have no such problem. They are static, public and worth indexing — give all 23 their own card and their own metadata.

  property="og:description"

  property="og:image"

Add `DefinedTerm` structured data — these pages are literally definitions, and it is the one schema type that fits without inventing claims:

```html
<script type="application/ld+json">
  {
    "@context": "https://schema.org",
    "@type": "DefinedTerm",
    "name": "xmin horizon",
    "description": "The oldest snapshot anyone still holds. Vacuum may not touch anything newer, no matter how you tune it.",
    "inDefinedTermSet": {
      "@type": "DefinedTermSet",
      "name": "robovac arcana",
      "url": "http://robovac.hannesmoser.at/arcana"
    },
    "url": "http://robovac.hannesmoser.at/explain/xmin-horizon"
  }
</script>
```

## 4. Generating the per-term and per-report cards

`card-template.html` is a standalone 1200 × 630 document with `{{TOKENS}}`. Two ways to render it:

**Playwright (highest fidelity — real IBM Plex, real `oklch()`):**

```js
import { chromium } from "playwright";
const browser = await chromium.launch();
const page = await browser.newPage({
  viewport: { width: 1200, height: 630 },
  deviceScaleFactor: 1,
});
for (const term of terms) {
  const html = template
    .replaceAll("{{KIND}}", term.kind)
    .replaceAll("{{ROUTE}}", "/explain/" + term.key)
    .replaceAll("{{TITLE}}", term.title)
    .replaceAll("{{BLURB}}", term.blurb);
  await page.setContent(html, { waitUntil: "networkidle" });
  await page.screenshot({ path: `public/brand/og/explain-${term.key}.png` });
}
```

Run it in CI, commit the output, serve it statically. 23 cards take a few seconds and never need to be generated at request time.

**@vercel/og / satori (edge-rendered, on demand):** works if you need report cards built per request. Two constraints to plan for: satori does not support `oklch()` — convert the warning tone to its sRGB hex (`#c98a4b`) — and you must supply the font files as buffers; the Google Fonts `<link>` does nothing there.

Whichever you pick, the type sizes in the templates are deliberate. Nothing on a card is under 22px at 1200 wide, because a card in a Slack sidebar renders around 360px across — a third of the design size.

## 5. Before rollout

1. **Absolute URLs.** `og:image` must be fully qualified with scheme and host. Relative paths are silently dropped by most scrapers.
2. **HTTPS.** X/Twitter will not render a card from an `http://` image. Ship TLS before you ship the cards.
3. **Optimise the PNGs.** They are canvas/browser output. `oxipng -o 4 --strip safe social_kit/*.png` is lossless. Avoid `pngquant` on these — they contain antialiased type and the warning tone.
4. **Keep every card under 1 MB, ideally under 300 KB.** WhatsApp gives up around 600 KB, and several scrapers stop at 5 MB but time out long before that.
5. **Serve `Content-Type: image/png`** and a stable URL. Scrapers cache aggressively by URL — if a card's copy changes, change its filename (or add a content hash), because re-scraping is not something you can rely on.
6. **Cache headers.** Immutable, long TTL for hashed card filenames; short TTL for `og-default.png` while you are still iterating on it.
7. **Test with the real validators**, not by pasting into a chat and hoping: Facebook's Sharing Debugger, X's Card Validator, LinkedIn's Post Inspector, and `curl -A "facebookexternalhit/1.1" <url>` to see exactly what a scraper receives from a JS-rendered app. That last one is the check that matters most for this product — if your report route only sets its meta tags client-side, the scraper sees none of them.
8. **Add `sitemap.xml` and `robots.txt`.** The sitemap should list `/`, `/mcp`, `/arcana` and the 23 explain URLs, and nothing else. `robots.txt` should disallow the report route explicitly.

## 6. Copy that ships with the cards

Keep the tone the product uses: statements of fact, exact figures, no adjectives.

- Site tagline: **Postgres vacuum settings, explained and tuned.**
- Sub: **one table · one link · no account**
- Description: **Take a statistics snapshot of one Postgres table and see what autovacuum is doing, what it should do, and the exact ALTER TABLE that gets you there.**
- Report card verdict: the report's own generated sentence, truncated at two sentences. Do not write a separate marketing line for it — the verdict is the strongest copy on the page precisely because it is computed.
